# ADR-009: Queued exports and notifications

## Status

Accepted

## Context

Email/SMS delivery, PDF generation, report export, and cache invalidation are slow or
externally dependent and must never run inside a MongoDB transaction or block the request that
triggered them.

## Decision

`apps/worker` runs BullMQ queues backed by Redis (`notifications`, `exports`,
`alert-evaluation`, `reconciliation` -- see `apps/worker/src/queues/queueNames.ts`). Jobs are
only enqueued after the triggering database transaction commits. Job payloads carry IDs, not
full sensitive documents, and processors are idempotent with bounded retries and dead-letter
handling. Scheduled jobs acquire a Redis distributed lock (`apps/worker/src/lock`) before
running, so only one worker instance executes a given scheduled job at a time.

## Consequences

- A crashed worker can safely re-process a job without double-sending a notification or
  double-exporting a report, because processors are idempotent.
- Report/export data is generated by querying source records at export time, never copied into
  a separate mutable `reports` collection.
